Linear Algebra ​

Standard LinearAlgebra functions work directly on ROCArray, dispatching to AMD's rocBLAS (dense BLAS) and rocSOLVER (LAPACK-style factorizations). You write ordinary Julia linear algebra; the GPU libraries are used automatically.

Supported out of the box on ROCArray:

  • Matrix–matrix and matrix–vector products (*, mul!), including mixed- and low-precision (Float16) matmul.

  • BLAS level-1 operations: dot, norm, axpy!, axpby!, rmul!.

  • Triangular solves and \ (linear systems, LU-based).

  • Factorizations: cholesky, lu, qr, svd.

julia
julia> A = ROCArray(Float32[4 1; 1 3]);

julia> b = ROCArray(Float32[1, 2]);

julia> x = A \ b;                       # solve, LU via rocSOLVER

julia> Array(A * x) ≈ Array(b)
true

julia> C = cholesky(A);                 # Cholesky factorization

julia> Array(C.U' * C.U) ≈ Array(A)
true

Element types follow rocBLAS/rocSOLVER: Float32, Float64, ComplexF32, and ComplexF64 (with Float16 also supported for matmul).

Singular value decomposition ​

svd, svd!, and svdvals run on ROCMatrix via rocSOLVER. The alg keyword selects the backend. QRAlgorithm(), the default, is bidiagonalization and QR iteration (gesvd) and is accurate for every singular value, like LAPACK on the CPU. JacobiAlgorithm() is rocSOLVER's Jacobi method (gesvdj): several times faster, but it works on A'A, so singular values below sqrt(eps)·σ₁ and their vectors are inaccurate without any indication; use it for well-conditioned matrices when speed matters. Known rocSOLVER issue (rocm-libraries#15788): for a rank-deficient ComplexF32 matrix, gesvd may return an unnormalized singular vector for a zero singular value.

julia
using AMDGPU.rocSOLVER: JacobiAlgorithm, QRAlgorithm

F = svd(A)                              # QR iteration by default; F.U, F.S, F.Vt
s = svdvals(A)                          # singular values only
Ff = svd(A; full = true, alg = JacobiAlgorithm())

Because svdvals is supported, so is cond. (opnorm(A, 2) is not yet available — it relies on scalar indexing internal to LinearAlgebra.)

Direct library access ​

Lower-level routines are available in the AMDGPU.rocBLAS and AMDGPU.rocSOLVER submodules for cases the generic interface does not cover — for example batched factorizations, or the raw gesvd! (QR) and gesvdj! (Jacobi) SVD kernels.

Device-side scalars ​

The scalar arguments of the rocBLAS wrappers (e.g. alpha and beta) can reside on the device, so that they don't need to be known on the host when an operation is enqueued — for example because a previous operation computed them. Pass an AMDGPU.ROCRef, or a one-element ROCArray; scalars on the host can still be passed as numbers, and the two can be mixed (host-side scalars are then written to the device, which is ordered on the stream without synchronizing). Routines that return a scalar (dot, dotc, dotu, nrm2, asum) accept an extra argument to write the result into, which avoids synchronizing with the host when it is a device-side scalar:

julia
x, y = AMDGPU.rand(Float32, 1024), AMDGPU.rand(Float32, 1024)

d = ROCRef{Float32}()
rocBLAS.dot(length(x), x, 1, y, 1, d)  # d = x ⋅ y, without synchronizing
rocBLAS.scal!(length(x), d, x, 1)      # x .*= d
d[]                                    # copy to the host

ROCRef(A, i) refers to element i of the array A, without copying it.

The Givens rotation routines rotg! and rotmg! overwrite their scalar arguments, so these can't be copied between the host and the device: either pass them all as host Refs, or all on the device. That makes it possible to construct a rotation on the device and apply it with rot! or rotm! without synchronizing. rotg(a, b) and rotmg(d1, d2, x1, y1) compute a rotation from host values instead.

AMDGPU.ROCRef Type
julia
ROCRef{T}()
ROCRef{T}(x)
ROCRef(x)
ROCRef(A::ROCArray, i::Integer=1)

A reference to a single value of type T that resides in GPU memory, e.g. to pass a device-side scalar to a library routine. The first three forms allocate a new value (optionally initialized to x), while the last one refers to element i of the (strided) device array A without copying it.

Reading a reference with r[] copies the value to the host, after the operations on the current stream have completed. Writing it with r[] = x (or constructing it from a value) is ordered on the current stream, but doesn't wait for it: the host can continue right away.

julia
alpha = ROCRef(2f0)
rocBLAS.scal!(length(x), alpha, x, 1)   # scale by a scalar that resides on the device

result = ROCRef{Float32}()
rocBLAS.dot(length(x), x, 1, y, 1, result)  # keep the result on the device
result[]
